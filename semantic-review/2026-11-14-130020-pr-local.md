# Backend verdict engine: fallback marking, confidence scoring, and opt-in human override

The change adds four behaviors to the verdict pipeline. `grade_pair` now distinguishes an LLM verdict from a verdict produced when the LLM layer could not run, tagging the latter `verdict_source='deterministic-fallback'`. A new pure function `compute_confidence` blends vector similarity, predicate agreement, and per-layer certainty into a `claim_links.verdict_confidence` column written on every graded UPDATE. `POST /api/reviews` gains an optional `override=true` that routes the decision through `apply_human_verdict`, which stamps `verdict_source='human'` and is protected from later machine regrades by a guard in `grade_links`. Migration 003 adds the enum value, the confidence column, and two indexes on the `claims` side, all additively.

Watch for: the human-override guard holds end to end (confirmed), but `compute_confidence` is excluded from the `changed` comparison in `grade_links`, so pre-migration rows with a NULL confidence are never backfilled unless the verdict itself changes or the link is a `touch_id` (confirmed). The `agree` override writes an UPDATE even when the verdict is unchanged (confirmed, intended, but worth noting against the no-op constraint).

**Verdict**: APPROVED

## High-level view

`llm_verdict` now returns a fifth `available` flag that is `False` for both the no-key short-circuit and the exception path, and `grade_pair` maps `available=False` to `deterministic-fallback` while keeping the loose `possible_match` candidate. A working key produces the same `llm` source as before.

The human-override guard works across every regrade path. `apply_human_verdict` commits the `verdict_source='human'` UPDATE before `recheck_page` runs (each `db.execute` opens its own connection and commits), so when recheck re-reads the link through `fetch_pairs_by_ids`, the guard in `grade_links` sees `human` and skips. The `grade_unmatched` path can't touch an overridden link either, since an overridden link has a real verdict and is no longer `'unmatched'`. The decision-to-verdict mapping is defensive: unknown current verdicts fall back to `unverifiable` rather than crashing.

Confidence scoring is a pure function, but its persistence has one asymmetry. `verdict_confidence` is written inside the UPDATE, yet it is not part of the `changed` tuple that gates whether the UPDATE runs. A row whose verdict, relation, and candidate_confidence are all unchanged but whose confidence would newly compute (NULL → a value on a pre-migration row) is not updated unless it is a stale/focus `touch_id`. This is consistent with the no-op-avoidance design and not a correctness bug, but it means confidence backfill is incremental, not immediate.

The API surface is additive. `override` defaults to `false` and the response gains an `override` field (null for non-override calls); `verdict_confidence` is added to the `/compare` link projection and the extension annotation projection. Migration 003 uses `IF NOT EXISTS` and `system_versioning_alter_history = KEEP`, so it is replayable and preserves SVT history. The enum `MODIFY` is not guarded by `IF NOT EXISTS` (not supported for enum widening) but is idempotent in effect.

### Fallback marking distinguishes "no model ran" from "model said possible_match"

`llm_verdict` returns a five-tuple now, with the trailing `available` flag false on both the no-key short-circuit and the `except Exception` degrade path. Both of those paths already returned the same loose `("possible_match", "unknown", None, …)` candidate, so the verdict and relation a reviewer sees are unchanged; only the source label differs. `grade_pair` keeps that candidate and relabels it `deterministic-fallback`:

```python
verdict, relation, confidence, rationale, available = llm_verdict(a, b)
if not available:
    return verdict, SOURCE_FALLBACK, rationale, relation, confidence
return verdict, SOURCE_LLM, rationale, relation, confidence
```

The deterministic layer short-circuits before `llm_verdict` is ever called, so a true deterministic verdict keeps `verdict_source='deterministic'` and is never mislabeled as a fallback.

### Human-override guard prevents reverts across every regrade path

The guard lives at the top of the `grade_links` loop:

```python
if p.get("verdict_source") == SOURCE_HUMAN:
    results.append({"id": p["link_id"], "before": p["verdict"],
                    "after": p["verdict"], "changed": False})
    continue
```

The question is whether any regrade path can reach an overridden link without going through this guard. Tracing the `create_review` override flow:

```
apply_human_verdict(link_id)   # UPDATE … verdict_source='human' … (commits)
      ↓
recheck_page(page_id, [link_id])
      ├── grade_unmatched(page_id)      # WHERE cl.verdict = 'unmatched'  → can't hit an overridden link
      └── grade_links(fetch_pairs_by_ids(stale + focus))  # re-reads verdict_source='human' → guard skips
```

Because `db.execute` opens its own connection and calls `conn.commit()` before returning, the `human` stamp is durable before `recheck_page`'s SELECT runs. `fetch_pairs_by_ids` re-reads the row, so the guard sees the freshly committed source. An overridden link also no longer satisfies `cl.verdict = 'unmatched'`, so `grade_unmatched` cannot regrade it. Both machine paths are covered.

The decision mapping is defensive against unexpected current verdicts:

```python
elif decision == "disagree":
    after = HUMAN_DECISION_VERDICT["disagree"].get(before, "unverifiable")
```

A current verdict not in the disagree table resolves to `unverifiable` rather than raising. The reviewer gets no signal that their disagreement had no concrete target (issue 3), but the pipeline never crashes.

### Confidence persistence is gated by the verdict-change check, not the confidence value

`compute_confidence` is a pure 0..1 blend: 0.35 similarity + 0.30 predicate agreement + 0.35 layer certainty, with certainty 1.0 for deterministic/human, the LLM's self-reported confidence for `llm` (0.5 when the model gave no usable number), and 0.25 for fallback. Bounds are clamped and the result rounded to 4 places.

The persistence path has one asymmetry. In `grade_links`:

```python
vconf = compute_confidence(a, b, source, p.get("similarity"), confidence)
changed = (verdict, relation, confidence) != (
    p["verdict"], p.get("relation"), p.get("candidate_confidence"))
if changed or p["link_id"] in touch_ids:
    execute("""UPDATE claim_links SET … verdict_confidence = %s, … WHERE id = %s""", …)
```

`vconf` is written when the UPDATE fires, but it is not itself a trigger for the UPDATE. A pre-migration row with `verdict_confidence IS NULL` whose verdict, relation, and candidate_confidence are all still current will not be updated — so its confidence stays NULL — unless it is a stale or focus `touch_id`. For newly graded links this never bites (an `unmatched` → graded transition always changes the verdict, so `vconf` is written). The effect is only on the backfill of rows graded before the migration: it happens incrementally as those links are otherwise regraded, not in one sweep. This matches the project's deliberate no-op-avoidance rule (no SVT row for a true no-op), so it is a design trade-off, not a bug. If the demo needs every row populated, a one-time backfill UPDATE is the fix (issue 1).

### SVT safety and migration shape

Every write to `claim_links` in this change is a plain `UPDATE … WHERE id = %s` (`grade_links` and `apply_human_verdict`); there is no `DELETE` or `DELETE HISTORY` on the table, so system versioning records each verdict transition as a new row version as required. Canonical `(min_id, max_id)` link ordering is untouched — nothing in the diff reorders `claim_a`/`claim_b` or re-keys links.

Migration 003 is replayable: the column add and both index adds use `IF NOT EXISTS`, and `SET @@system_versioning_alter_history = KEEP` preserves history rows across the `ALTER`. The one unguardable statement is the enum `MODIFY` (issue 4), which enum widening cannot express as `IF NOT EXISTS`; it is idempotent in effect because re-running it sets the same enum definition. The schema.sql change mirrors the migration (same new column, enum value, and the two `claims` indexes), keeping a fresh `CREATE` in sync with an upgraded database.

### Backwards compatibility

The `Review` model adds `override: bool = False`, so existing clients that omit it keep the audit-log-plus-recheck behavior (user decision #4) unchanged. The response gains an `override` key that is `null` for non-override calls, which is additive. `verdict_confidence` is surfaced additively in both the `/compare` link projection (`main._annotation_link`) and `diff._fetch_links`; the SELECT column order changed but the callers read by key, so the reordering is harmless. `candidate_confidence` keeps its original meaning (raw similarity slot) and is not repurposed.

### Not tested

No automated tests accompany the change (consistent with the project's hackathon posture). The highest-value cases to verify manually before the demo: an override on a link then a recheck, confirming the verdict survives (the core Q1 guarantee); a `disagree` on a `definition_mismatch`/`unmatched` link, confirming the `unverifiable` fallback behaves acceptably; and `compute_confidence` boundaries (NULL similarity, missing predicate on one side, LLM confidence absent) since it is pure and cheap to unit-test.
